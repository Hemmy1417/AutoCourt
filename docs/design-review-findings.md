# Design-review findings (pre-implementation)

Raw output of the four-lens adversarial review, kept verbatim for the reconciliation commit.


## Lens: evidence-model

### Recommendation

Build MODEL A, AMORTIZED (call it A-prime): all judged bytes on-chain, but entered per-item, never as one mega-packet. Per-document text travels in its own submit-evidence-text write (normalized extract <= 6,000 chars; whole JSON argument <= 8,000 chars — the envelope CredenceLend proved live in its 28/28 attack arc via the 8,000-char input_bundle, with InsureShield's live 12,000-char definition writes as headroom, not as the bound). submit_assessment carries only claims + evidence-id list + manifest root (<= 8,000 chars). Panel budget: <= 12 items per assessment (8 first-round + 4 appeal, CredenceLend's exact split), total judged text <= 72,000 chars — inside both spines' proven prompt envelopes (CredenceLend 12 x 8,000; InsureShield 6 x 12,000) — and the leader findings payload capped at 300,000 chars (CredenceLend's parse cap; it carries findings and quotes, never text). Original binary files NEVER travel: only their sha256 does, alongside a second hash over the normalized text (defect 3). Run a disposable-deploy calldata probe on StudioNet before freezing bounds.

Why not B, from the letters and the operational record: B's integrity is fine (CredenceLend's every-node fetch-hash-verify satisfies S39/S8 at entry — that is why it survived 103 live tx), but B's AVAILABILITY is the killer for AutoCourt specifically. The only PROVEN evidence host is commit-pinned GitHub raw, which cannot host private user uploads; app-hosted URLs make the operator's uptime a consensus input (StudioNet rate limits and the Verda-arc host stall are the operational record of exactly this), give the operator a censorship lever (force SOURCE_UNAVAILABLE at will — hash makes tampering detectable, availability stays his), turn every reachability split into a burned UNDETERMINED round, and make APPEALS decay with hosting (S14/S28 re-verification needs the bytes served forever — an appeal right contingent on the operator still paying for Vercel is an S17-shaped trap). And B buys nothing back: the same app builds the normalized text either way (extractor trust identical), and B's privacy is illusory — the URL sits on-chain and validators fetch unauthenticated, so adjudicated bytes are public in B too, just less honestly. Why not single-tx A: defect 1 — unproven calldata ceiling at the heart of the architecture.

Exact failure behavior for A-prime: a validator 'unable to obtain bytes' is impossible by construction (bytes are consensus state); LLM/transport failure → TRANSIENT UserError → tx fails, state unchanged, bounded worker retries then FAILED-with-retry; malformed/ungrounded output → run recorded REJECTED, prior record stands; protocol UNDETERMINED → no contract outcome, poll and retry. SOURCE_UNAVAILABLE is documented RESERVED (defect 4). Exact privacy statement the docs must carry, verbatim shape: 'Adjudicated evidence is public: submitting an assessment permanently publishes the bounded normalized extract of every packet item, claim values, both hashes, and the panel's findings on a public chain. Originals are never published — only their sha256. Private-by-default means private until included in a packet; inclusion is an explicit per-item consented act; redaction must precede submission and is impossible after.'

### Defects

**[blocking] ARCHITECTURE.md §4 (submit_assessment(packet_json)) + §3 (packet built at assessment time)**
- standard: S39 delivery risk / master template §6.8 (bound everything) — architecture-tier, redeploy-class if wrong
- problem: The design puts the ENTIRE evidence corpus in one transaction's calldata with no size argument. The proven live envelope from the spines is roughly 8-12KB per write: CredenceLend's only calldata-borne evidence bundle is capped at 8,000 chars (credencelend.py:2768) and that cap was exercised live in the 28/28 attack arc; InsureShield's largest calldata JSON is the 12,000-char policy definition (insureshield.py:601), exercised live at policy creation. NOTHING larger has ever ridden a StudioNet write in this portfolio — the spines' big text (8 docs x 8,000 / 6 docs x 12,000 bytes) traveled through validator FETCHES and prompt payloads, never through transaction calldata. An AutoCourt packet at product scale (>=8 documents x multi-KB extracts + claims + manifest) is 50-100KB of calldata — 6-12x beyond anything proven, discovered only at deploy time, and unfixable without a redeploy.
- fix: Amortize model A across writes so no single transaction exceeds the proven envelope: evidence text enters chain state via a per-item write (submit_evidence_text: id, declared type, both hashes, normalized text <= 6,000 chars; whole JSON argument <= 8,000 chars — the live-proven CredenceLend number, with InsureShield's 12,000 as headroom, never the bound). submit_assessment then carries only the claim set + evidence-id list + manifest root (<= 8,000 chars) and adjudicate(id) reads the already-stored bytes. Additionally run a disposable-deploy calldata probe on StudioNet (the validator-model-diversity practice: diagnose on a throwaway deploy BEFORE the canonical one) to measure the real ceiling before freezing bounds in get_config().

**[high] ARCHITECTURE.md — privacy is never stated (§2 mentions access control, §5 'DB caches, chain decides', §8 silent)**
- standard: Brief §15 (private-by-default evidence) + §16 ('unauthorized users cannot access private evidence') + S12 narrative honesty
- problem: Model A publishes every adjudicated evidence extract, permanently and irrevocably, in public chain state readable by anyone on the explorer. The docs currently let 'private-by-default' and calldata-borne evidence coexist unreconciled — a reviewer will read the brief's privacy demand against the architecture and find a contradiction, and a §16 test asserting private evidence would be asserting something the architecture makes false for adjudicated items. (Model B is NOT better here: CredenceLend stores the URL on-chain and validators fetch unauthenticated, so hash-capability URLs make adjudicated bytes public too — minus the honesty about permanence.)
- fix: Add the exact statement to ARCHITECTURE.md and the threat model, and mirror it as a UI consent step: 'Adjudicated evidence is public. Submitting an assessment publishes, permanently, on a public blockchain: the bounded normalized text extract of every packet item, the claim values, both hashes, and the panel's findings and quotes. Original files are never published — they remain in access-controlled app storage; only their sha256 fingerprints go on-chain. Private-by-default means: private until included in a submitted packet; inclusion is an explicit per-item consented act; redaction must happen before submission and is impossible after.' Scope the §16 privacy tests to originals and un-adjudicated items.

**[high] STANDARDS-MAP.md §2 (RECORDED = 'byte-identical to an item in the appealed run's manifest, verified by hash') + ARCHITECTURE.md §2/§3 (sha256 computed over the uploaded FILE; 'the hash, not the path, is the identity')**
- standard: S21 (a digest must cover the bytes actually judged), S14/S28/S36 (appeal re-judges the recorded snapshot)
- problem: The manifest as designed binds original-file hashes, but the panel judges the NORMALIZED TEXT. If RECORDED is verified against the original-file sha256, a readjudication packet can pair the same original hash with DIFFERENT extracted text (a re-extraction, an 'improved' normalization) and still be tagged RECORDED — the appeal panel then re-judges bytes the first panel never saw, under a tag that vouches for identity. This is GroundTruth's S21 defect shape verbatim (hash over body[:12000], stored excerpt[:1500] — a digest covering bytes nobody re-checks).
- fix: Each manifest entry carries BOTH hashes: (id, original_sha256, normalized_text_sha256), and the manifest root is over that triple. RECORDED requires equality of the normalized-text bytes — directly comparable since both runs' texts live in chain state under model A. State in the docs that the manifest binds the judged bytes, not only the source file.

**[medium] ARCHITECTURE.md §6 (SOURCE_UNAVAILABLE listed in the implemented enum, no reachability note)**
- standard: S12 narrative honesty; brief §13 ('if external information is unavailable, return SOURCE_UNAVAILABLE')
- problem: Under model A there is no fetch, so SOURCE_UNAVAILABLE is unreachable — in CredenceLend it is precisely the all-nodes-agree-unreachable/hash-mismatch verdict (credencelend.py:1999-2000), a branch AutoCourt's contract cannot enter. Docs listing an emittable verdict the contract can never produce claim behavior the code does not have; conversely, silently dropping it breaks the brief's enum contract.
- fix: Keep the value in the shared enum but document it as RESERVED: reachable only if a later version adds a contract-side fetch (which then inherits CredenceLend's exact semantics — see next defect). Map the actual model-A analogues explicitly: extraction unavailable → item marked UNEXTRACTED, disclosed to the panel, sufficiency gate → INSUFFICIENT_EVIDENCE / PHYSICAL_INSPECTION_REQUIRED.

**[medium] ARCHITECTURE.md §4 (failure fails closed) — the failure table is incomplete for the evidence model chosen**
- standard: S5, S26, master template §9.5 (protocol UNDETERMINED vs contract verdict)
- problem: The docs state fail-closed for malformed model output but never write down the full model-A failure ladder, and 'what happens when a validator cannot obtain bytes' is exactly the question a judge will ask of an evidence model. Under model A the answer is structural and should be claimed as such; under any future fetch it must be CredenceLend's proven behavior, which the docs do not record.
- fix: Add the failure table: (a) evidence bytes are consensus state — a validator 'unable to obtain bytes' is impossible by construction; the only byte-level failure is a state read failure = transaction failure, state unchanged. (b) LLM/transport failure in the round → UserError(TRANSIENT) → tx fails, state unchanged, worker retries bounded-N then Assessment→FAILED with retry (S26 exit). (c) Malformed/ungrounded model output → run recorded REJECTED, previous record stands. (d) Protocol-level UNDETERMINED → no contract outcome; poll and retry, never mapped to a verdict. (e) If a fetch is ever added: all nodes unreachable-or-hash-mismatch → SOURCE_UNAVAILABLE (credencelend.py:1999); ANY reachability split → validator disagreement → no state change (credencelend.py:1822-1837) — never a verdict from partial sight.

**[medium] STANDARDS-MAP.md §1 ('Corroboration-at-entry is structural, not procedural')**
- standard: S38 (a proof claims only what its mechanism asserts) / S12
- problem: Overclaim. Calldata gives byte-AGREEMENT at entry — every validator judges identical bytes — but not extraction FIDELITY: the app is the sole extractor, and every validator faithfully judges whatever the app's pipeline produced from the original file. S39 is satisfied for the bytes; the app-as-extractor trust is a residual limitation the sentence currently papers over, and a judge who reads 'structural' as covering the whole entry path will find the gap.
- fix: Split the claim in two sentences: byte-identity at entry is structural (calldata); extraction fidelity is a stated limitation, mitigated by (a) the stored original + its on-chain sha256 letting anyone recompute the deterministic extraction after the fact, (b) the counterparty's own upload channel as the corrective path (S34 corroboration classes already price a one-sided record), (c) extraction code committed in the repo and versioned in the packet.


## Lens: trust-story

### Recommendation

MODEL CHOICE (the open fork, from this lens): keep model A — calldata — but in Adjudex's proven chunked shape, not one mega-packet. The decisive argument: model B buys NOTHING against the app-as-oracle problem, because the app both serves the URL bytes and committed the hash — validators fetching from the operator's server and verifying the operator's own hash corroborates the operator against itself (a hash-capability URL is S39's 'digest over bytes its author chose', distributed). Meanwhile model B imports real costs the spines document: CredenceLend's fail-soft ROW_UNAVAILABLE path means a single origin outage degrades runs to SOURCE_UNAVAILABLE, and hash-as-capability URLs make private-by-default evidence (brief §15) effectively public to anyone holding the link. Model A gives byte-identical evidence by construction, satisfies S39 structurally (Adjudex was ruled S39-safe on exactly this ground), and has live StudioNet precedent for realistic sizes: Adjudex committed ≤6,000-char items, 12 per commit, 40 per record; CredenceLend's fetch budget (8,000 bytes × 12 items ≈ 96KB) shows the prompt budget is equivalent either way. The unknown single-tx calldata ceiling is dodged by chunked commits + seal, which no spine has ever needed to exceed. TRUST CLAIM (three sentences, README seed): "AutoCourt's operator authenticates users, stores files, extracts text, and assembles the assessment packet — nothing about consensus changes that, so the packet is the operator's testimony about the evidence, made tamper-evident by per-item hashes and an on-chain manifest. What GenLayer removes is everything downstream: no party, including the operator, authors the verdict — a validator panel judges the recorded packet, deterministic public code derives every verdict and floor from findings the panel agreed on, and no one can re-run, rewrite, or selectively display that record, because every run and manifest is permanently on chain for either party to check. So a buyer is protected outright from a biased or bought judgment and from a rewritten record, and is protected from a curated packet by detection rather than prevention: committed hashes, intake receipts, and immutable runs make omission and alteration provable by the party wronged." S9: the adjudication is load-bearing without money ONLY via the two-party adversarial reliance — a buyer must be able to rely on a verdict the seller-facing platform provably cannot author — and the Verda precedent supports exactly this: Project credit for a no-money adjudication whose verdict IS the product, granted with a single ask, evidence provenance. So AutoCourt's Project-credit case stands or falls on the intake-provenance defects above (contract-derived corroboration classes, attributable uploads, extraction binding, no verdict-shopping), not on bolting on a bond; fix those and the STANDARDS-MAP §7 DECISION-terms answer to S9 is true as written.

### Defects

**[blocking] ARCHITECTURE.md §3 (packet: 'corroboration class derived in code') + STANDARDS-MAP §3**
- standard: S34 (corroboration floor enforced in code), S7 (every decisive field inside what validators check), S27
- problem: The corroboration class decides verdict ceilings (FIRST_PARTY can never reach VERIFIED), but §3 derives it in the APP's packet-builder — operator code. The contract's floor then reads a label the operator (or a bug) authored: label everything CORROBORATED and the S34 floor is bypassed without any validator noticing, because the class arrives in calldata as fact. This is exactly the field class S7 exists for — decisive, and outside anything consensus re-derives.
- fix: The packet carries only raw per-item facts (uploader role, hashes, timestamps, anchor references); the CONTRACT re-derives the corroboration class deterministically inside the judged code path, and the app's copy is display-only. State this split explicitly in both docs.

**[high] ARCHITECTURE.md §2 (auth: email+password, roles contextual) vs STANDARDS-MAP §3 (COUNTERPARTY = 'parties with opposing interests')**
- standard: S27 (subject must not control identity), S34 ladder (BILATERAL requires a counterparty WALLET-SIGNED ack — AutoCourt's COUNTERPARTY has no signature at all)
- problem: With free email accounts and no cryptographic attribution, 'opposing interests' is unverifiable: a seller with two inboxes — or the operator — mints COUNTERPARTY uploads and manufactures CORROBORATED, feeding the floor designed to price S27 with input from the party it prices. Adjudex's accepted ladder put app-asserted attribution BELOW wallet-signed; this design puts it at the top.
- fix: Either (a) per-user keypairs sign each item's sha256 at upload, signatures ride in the packet so validators verify attribution, or (b) demote app-asserted COUNTERPARTY to a disclosed claim (S31 treatment: 'the platform asserts these accounts are distinct parties — unverified') and reserve CORROBORATED for integrity-bound independent anchors; document the residual in the threat model either way.

**[high] ARCHITECTURE.md §3 + STANDARDS-MAP §1 ('deterministic software; stored originals let anyone recompute')**
- standard: S39 spirit (corroborate where evidence ENTERS the record), S12 narrative honesty, brief §16 ('evidence is never silently discarded')
- problem: Validators corroborate the packet bytes perfectly — but those bytes are the operator's EXTRACTION of the original file, and nothing in the record binds extracted text to original bytes in a way a third party can check without the operator's cooperation. Altered or truncated extraction produces a fully consensus-blessed verdict over fabricated text; 'anyone can recompute' is false while originals sit private in operator storage with no pinned extractor version and no committed text hash.
- fix: Commit per item BOTH the original-file sha256 AND the normalized-text sha256, plus the pinned extractor version string, in the on-chain manifest; guarantee both parties of a judged run can download originals and normalized text; ship a repo script (verify-extraction) that recomputes text-hash from an original; classify extraction honestly as detectable-not-prevented in README and threat model.

**[high] ARCHITECTURE.md §4 submit_assessment(packet_json) — one write carries the whole packet**
- standard: Template §6.8 (bound everything) endangered by an unknown StudioNet calldata ceiling; the proven spines never sent one large packet
- problem: No sibling has ever pushed a full evidence corpus through one transaction: CredenceLend commits tiny (url, sha256) rows and fetches; Adjudex — the only live model-A precedent — commits text in CHUNKS of ≤12 items × ≤6,000 chars, never one mega-calldata. A 13-screen product's worst-case packet (dozens of items × bounded text + claims + pre-findings) in a single tx bets the core write path on an unmeasured platform limit.
- fix: Adopt Adjudex's proven shape: chunked evidence commits (per-item char cap ~6,000, bounded items per commit) building the stored record, then a seal/submit that fixes the manifest root, then adjudicate over STORED bytes. Publish every cap via get_config. Keep model A — see recommendation.

**[medium] ARCHITECTURE.md §4 — adjudicate(id) re-runnability unspecified**
- standard: S12 (what the README will claim), S25-adjacent binding of a case to one ruling per record state
- problem: Nothing says a second adjudicate() over a byte-identical packet is refused. Panel output is nondeterministic across runs, so the operator can re-roll until a favorable run exists and render that one; all runs are on-chain (detectable) but the design should make verdict-shopping unrepresentable, not merely auditable.
- fix: Contract refuses adjudication of an unchanged manifest outside readjudicate(); get_verdict() defines 'current' as the latest run deterministically; the report UI shows total run count and links every run.

**[medium] ARCHITECTURE.md §3/§5 — no party-facing intake receipt**
- standard: Brief §16 ('evidence never silently discarded'), S40 (the verification path must be reachable in the UI)
- problem: Omission is the operator's cheapest attack: quietly drop the buyer's counter-evidence from the packet. The manifest is on-chain, but no designed surface lets a party confirm THEIR item's hash appears in the judged manifest — detection exists in principle and nowhere in the product.
- fix: Per-run manifest view in the UI listing (id, sha256) with each party's evidence marked 'in run N' / 'not in any run'; a buyer's disputed-claim flags must appear in the packet or the run records their absence. Add the corresponding invariant test.

**[medium] ARCHITECTURE.md §8 delete-GenLayer paragraph + STANDARDS-MAP §7**
- standard: S12 narrative honesty, S9 economic substance
- problem: 'Remove GenLayer and one party's backend becomes the authority on every claim' overclaims: the operator's backend ALREADY authors the packet — identity, extraction, assembly. As written it hands a judge the rebuttal ('the operator curates everything upstream; a centralized LLM plus an audit log does this more efficiently' — Agora's exact S9 letter). The true, defensible claim is layered: consensus eliminates operator authorship of the JUDGMENT and the RECORD; intake is tamper-evident, not trustless.
- fix: Rewrite §8 as the layered claim and add the brief-§17-required threat-model doc with the explicit table: eliminated-by-design (verdict authorship, record rewriting, selective display vs the chain, silent re-rolls once defect 5 is fixed) / detectable-after-the-fact (extraction alteration, omission — by the wronged party, via committed hashes + intake receipts) / honest limitation (operator can refuse service; app-asserted party identity; originals custody).

**[low] Design gap — operator submission liveness**
- standard: S26 (named mover for every non-terminal state), threat-model completeness (brief §17)
- problem: Only the operator's worker submits transactions; an operator can stall a buyer-requested reassessment forever. §7's PROCESSING timeout goes to FAILED-with-retry, but retry is also operator-gated — censorship is undocumented.
- fix: Document it: AutoCourt is not censorship-resistant; the operator can decline to run an assessment but cannot forge or alter one. One sentence in the threat model and README trust section; optionally note that submit-from-own-wallet is a possible future path.


## Lens: contract-shape

### Recommendation

Contract-surface/verdict-model verdict: the surface shape (submit/adjudicate/readjudicate/views, findings-in-model verdicts-in-code) is the proven spine shape, but §6 as written cannot ship. Required spec deltas, in order of load-bearing-ness: (1) partition the 13 values — 7 claim-level verdicts (brief §4.6's own set), 3 code-derived flags (mileage_conflict, odometer_rollback_indicated = conflict + NOT_EXPLAINED explanation finding, diagnostic_concern_supported), assessment-level rollup by fixed precedence, and REJECTED/SOURCE_UNAVAILABLE demoted to run/item statuses — and key the S34 floor on an adverse:bool attribute, never a name list (as written, POSSIBLE_ODOMETER_ROLLBACK bypasses the floor that blocks only CLAIM_CONTRADICTED). (2) Corroboration class moves INTO the contract, derived per (claim,item,direction) edge from primitive calldata facts + equivalence-agreed finding status; ladder INDEPENDENT > ADVERSE (recorded opposing dispute stake, distinct account) > FIRST_PARTY; same-account items never corroborate; VERIFIED requires INDEPENDENT because two colluding accounts trivially manufacture opposing-role 'CORROBORATED'. (3) Manifest commits (file_sha256, text_sha256, extractor_version); RECORDED appeal items are referenced by id and read from contract storage, never re-supplied — the current file-hash-only RECORDED check re-opens the exact Verda/Triggera 'internally consistent dossier' hole against the normalized text the panel actually read. (4) Replace 'verbatim' quote checking with CredenceLend's word-token grounding and drop-and-downgrade (REJECTED only for structural invalidity) — run-level REJECTED on one ungrounded quote hands adjudication availability to the weakest StudioNet model family, the exact live failure the spine already fixed. (5) confidence_band/next_action become code formulas; unresolved_questions is labeled non-consensus prose. On the fork, from this lens: neither spine proves ~100KB write calldata (proven live: ≤~2KB write calldata; 8KB/doc and ~300KB leader payloads through consensus), so if model A is chosen, stage packet submission (begin/append-verified-against-committed-hash/seal) so no single tx needs the unproven ceiling, and accept that SOURCE_UNAVAILABLE becomes an item-status and adjudicated text becomes permanent public calldata — both must be documented, not implied away.

### Defects

**[blocking] ARCHITECTURE.md §6 (verdict model) + STANDARDS-MAP §3 (corroboration floor)**
- standard: S34 (uncorroborated adverse finding), S7, model-diversity lesson 'one home per problem'
- problem: The 13-value enum has no declared partition into claim-level verdicts, code-derived flags, assessment-level rollups, and run statuses. Concrete failure 1: the S34 floor in STANDARDS-MAP §3 blocks only CLAIM_CONTRADICTED by name — POSSIBLE_ODOMETER_ROLLBACK, MATERIAL_CONCERN and DIAGNOSTIC_CONCERN_SUPPORTED are all adverse findings not named by the floor, so a buyer's sole uncorroborated upload can yield POSSIBLE_ODOMETER_ROLLBACK (a fraud accusation, strictly worse than the blocked CLAIM_CONTRADICTED) with zero corroboration. Concrete failure 2: a mileage claim contradicted by dated documents simultaneously satisfies MILEAGE_CONFLICT, POSSIBLE_ODOMETER_ROLLBACK and CLAIM_CONTRADICTED; with no precedence defined the report can say the claim is CLAIM_CONTRADICTED while the assessment says MILEAGE_CONFLICT and the rollback flag is silent — a contradictory report from one deterministic function. This is the enum-layer twin of the overlapping-questions split CredenceLend paid for live (SUSPICIOUS then NO VERDICT on the same facts).
- fix: Partition explicitly in the spec: (a) claim-level verdicts, exactly one per claim: VERIFIED, PARTIALLY_VERIFIED, CLAIM_CONTRADICTED, CONFLICTING_EVIDENCE, INSUFFICIENT_EVIDENCE, PHYSICAL_INSPECTION_REQUIRED, INCONCLUSIVE — matching brief §4.6's own six-way claim determination; (b) code-derived boolean flags, never claim verdicts: mileage_conflict (code-detected date/mileage inversion), odometer_rollback_indicated (= mileage_conflict AND panel explanation finding NOT_EXPLAINED — CredenceLend's LIQUIDATION_EXPLANATION pattern), diagnostic_concern_supported (panel symptom-support finding, brief §14); (c) assessment-level rollup: MATERIAL_CONCERN / the flags surfaced as MILEAGE_CONFLICT / POSSIBLE_ODOMETER_ROLLBACK / DIAGNOSTIC_CONCERN_SUPPORTED as headline of the report, derived by fixed precedence over (a)+(b); (d) run statuses, never verdicts: REJECTED (model output failed structural gate), SOURCE_UNAVAILABLE (see separate defect). Key the S34 floor on a direction attribute (adverse: bool) carried by every verdict and flag, never on an enumerated name list.

**[blocking] ARCHITECTURE.md §3 ('corroboration class derived in code' inside the APP-built packet) + STANDARDS-MAP §3**
- standard: S27 (subject controls identity and sources), S34 ladder, S7
- problem: Three stacked failures. (1) The class is derived in APP code and shipped inside the packet, so the contract enforces its S34 floor against an app-asserted label — the operator or a pipeline bug can stamp FIRST_PARTY items CORROBORATED and lift VERIFIED past the floor; the floor is then enforced against nothing. (2) COUNTERPARTY is inferred from role, and roles are free: auth is open email+password and 'buyer' is anyone a share link reaches, so a seller opens a second account, 'buys' their own listing, and uploads a supporting report — two items from 'parties with opposing interests' → CORROBORATED → VERIFIED is reachable by one person with two emails. Adjudex's BILATERAL rung worked because the counterparty was bound at case open with an adverse stake; here there is no stake and no identity. (3) The class is stored per ITEM but defined per favor-direction ('uploaded by the party the claim favours'), and the brief (§12) says one item can support or contradict MULTIPLE claims — a seller's defect disclosure is against-interest for the defect claim and self-serving for the 'fully disclosed' claim, so a single per-item label is ill-defined.
- fix: Spec deltas: the packet carries only primitive facts per item (uploader_account_id, uploader_role, upload/capture timestamps, the recorded dispute set naming which account disputed which claim before the run); the CONTRACT derives the class per (claim, item, direction) edge — deterministic from calldata facts plus the panel finding's supported/contradicted status, which is inside equivalence, so the derivation is S7-clean. Replace the either/or CORROBORATED with a distinct ladder: INDEPENDENT (item integrity-bound to a registrable external source) > ADVERSE (uploaded by an account with a recorded opposing dispute stake on that claim, distinct account id from every item it corroborates) > FIRST_PARTY. Rule in code: items from the same account_id never corroborate each other; VERIFIED (the seller-favoring ceiling) requires INDEPENDENT, because ADVERSE-class support is exactly what colluding accounts manufacture — opposing-role uploads may only strengthen adverse/contradiction findings, not lift VERIFIED. State plainly (S12) that account identity is app-attested and Sybil collusion is detectable only via same-hash/same-account rules, not preventable.

**[blocking] ARCHITECTURE.md §4 readjudicate row ('hash-verified against the stored manifest, tagged RECORDED') + §2/§3 (files hashed at upload; packet carries bounded NORMALIZED text)**
- standard: S28, S36, S39 ('internally consistent dossier'), S21 corollary (a digest must cover the bytes actually read)
- problem: The manifest sha256 is the ORIGINAL FILE hash (§2: 'files are hashed at upload; the hash is the identity'), but what the panel reads is the app's NORMALIZED EXTRACTED TEXT (§3). At readjudication a delta-packet item is tagged RECORDED by matching the file hash — which never covered the text the first panel judged. Concrete failure: run 1 normalizes a PDF to text containing a damning sentence; at appeal the app re-extracts (new extractor version, or operator tampering) to text without that sentence; file sha256 still matches, the item passes as RECORDED 'byte-identical', and the appeal panel faithfully reconsiders altered evidence under the same citation. This is the Verda/Triggera defect shape verbatim — a chain whose first link the hash never checked — flagged blocking twice in two days.
- fix: Manifest entries commit BOTH digests: (evidence_id, file_sha256, text_sha256, extractor_id/version), root over all fields. adjudicate stores the full normalized text on-chain (it arrived in calldata anyway); readjudicate accepts RECORDED items by evidence_id REFERENCE ONLY and reads the text from its own storage — re-supplied bytes for a RECORDED item are refused, making the altered-re-extraction attack unrepresentable rather than merely detectable. NEW items carry full text + both hashes and are tagged with uploader and post-verdict timestamp per S36.

**[high] ARCHITECTURE.md §4 bullet 'Failure fails closed (S5): ... a quote that does not ground → run records REJECTED' + STANDARDS-MAP §4 ('quotes must appear verbatim')**
- standard: CredenceLend validator-diversity lesson (S5 mis-applied); S16
- problem: Two errors the spine already paid to learn. (1) 'Verbatim' quote checking is the exact rule that split StudioNet model families on InsureShield/CredenceLend: \n-joined lines, quote/excerpt key variants, '4' for 'E4', enveloped answers — a character-exact check turned honest answers into downgrades and one live round ended with NO verdict. (2) Escalating a single ungrounded quote to run-level REJECTED is worse than the pre-fix spine: CredenceLend drops the quote and DOWNGRADES that one finding to its non-adverse state ([DOWNGRADE] print, raw quotes first), reserving rejection for structurally invalid output. As specced, one weak model family producing one ungroundable quote on one finding kills the whole adjudication — availability of the product's core verb hinges on the weakest validator family, and this is invisible in Direct Mode where mocks answer the fixture.
- fix: Spec deltas: grounding = CredenceLend's word-token rule (_quote_grounded: contiguous lowercase-alnum token runs in order, ellipsis/newline-split fragments, ≥2 words per fragment, QUOTE_MIN 8 / QUOTE_CAP 240 / MAX_QUOTES 3), with _ground_quote-style re-attribution across eligible evidence ids and acceptance of every quote shape (store only grounded). Failure ladder: ungrounded quote → drop quote; adverse state left with zero grounded quotes → downgrade that finding to UNDETERMINED/non-adverse ([DOWNGRADE] + raw quotes printed); REJECTED reserved for unknown enum / malformed structure / failed _parse_payload-equivalent. Mandate the disposable-deploy diagnostic pass ([DISAGREE] own-vs-leader with dissenter's own quotes, per _first_difference) before the canonical deploy.

**[high] ARCHITECTURE.md §6 vs build brief §5 ('Every verdict must include ... confidence level; unresolved questions; recommended next action')**
- standard: S7 (Froth origin: confidence is the archetypal field that moves outcomes outside equivalence), S12
- problem: The brief mandates per-verdict confidence level, unresolved questions, and recommended next action; §6 and the equivalence set never mention any of them. If confidence comes from the panel and is displayed (or ever gates anything), it is the exact Froth/Delphi S7 defect — an LLM value outside equivalence steering what a buyer relies on. If unresolved-questions/next-action prose is rendered without labeling, S12's 'consensus-checked' overclaim trap follows. The design currently has no home for three brief-required report fields.
- fix: Spec deltas: confidence_band is DERIVED IN CODE per claim from already-agreed inputs — a fixed formula over (corroboration class, finding states, extraction coverage), e.g. INDEPENDENT+consistent → HIGH, ADVERSE-only → MEDIUM, FIRST_PARTY-only or any UNEXTRACTED cited item → LOW — never a panel output. recommended_next_action is a deterministic table keyed by (claim verdict, flags) — e.g. PHYSICAL_INSPECTION_REQUIRED → named inspection type. unresolved_questions is the one free-prose field: panel-authored, outside equivalence, rendered with an explicit 'panel narrative, not consensus-checked' label (S12), and it is the vehicle for brief §14's 'explain what additional evidence would reduce uncertainty'.

**[high] ARCHITECTURE.md §3 ('deterministic pre-findings the code can compute' — computed by the APP, shipped in the packet) + §4 equivalence ('mileage-conflict flags')**
- standard: S7 (every field the report reads is deterministic-from-agreed-inputs or in equivalence), S31
- problem: Equivalence-set walk finds the gap: per-claim status ✓ (equivalence), severity band ✓, cited id sets ✓, inspection bit ✓, corroboration class ✗ (app-asserted — defect 2), and mileage-conflict flags ✗: the flag is computed by app code BEFORE the packet and shipped as data. Validators agree on the packet bytes, but the flag is then an unverified app assertion both steering the panel (presented as a code-detected fact — S31's exact shape) and read by the verdict function. If the app's sequence check is wrong or gamed (dates only present in unextracted images, say), the contract derives POSSIBLE_ODOMETER_ROLLBACK machinery from an echo. CredenceLend's pattern is the opposite: structured facts are parsed ON-CHAIN per node and code indicators re-derived inside _parse_payload by every validator.
- fix: Packet carries TYPED observation rows (evidence_id, doc_date, odometer_reading, source_field) — the brief's DiagnosticObservation shape — alongside the text; the CONTRACT recomputes mileage-sequence conflicts, duplicate-hash, and VIN-echo mismatch from those rows (deterministic from calldata, validator-recomputed exactly as CredenceLend's _plan/_parse_payload re-derives code indicators). A reading that exists only inside free text is not a typed row and cannot raise the code flag; it can only support a panel finding under equivalence. App-side pre-findings become at most a UI preview, never packet fields.

**[medium] ARCHITECTURE.md §6 SOURCE_UNAVAILABLE vs §4 'no contract-side fetch' (the open fork, verdict-model face)**
- standard: S12 (narrative honesty: an enum the contract can never produce), brief §13 ('if external information is unavailable, return SOURCE_UNAVAILABLE')
- problem: Under model A (calldata, no fetch) no source can ever be unavailable at adjudication time — SOURCE_UNAVAILABLE is dead code wearing a verdict's name, and a README documenting it implies a fetch path that does not exist. Under model B it maps cleanly to CredenceLend's ROW_UNAVAILABLE/BLOCKED row statuses. The enum member is silently taking a side in the unresolved fork.
- fix: Resolve per the fork decision and define it either way: model A → repurpose as an ITEM status surfaced in the report (extraction UNAVAILABLE / evidence present-but-unreadable, per §2's OCR-null adapter), never a claim verdict, and rename in the claim-level partition accordingly; model B → keep as the row status for a validator-side fetch failure, with CredenceLend's rule that fetch failure is UNAVAILABLE (fail-soft row), never an adverse finding (S5). Either way document which enum members are reachable and from where — the release-gate grep should assert every enum value has a producing code path.

**[medium] ARCHITECTURE.md §4 'Everything bounded' (no constants) — design gap**
- standard: Master template §6.8 (bound everything, with maxima), S10; calldata-ceiling question in the fork
- problem: No numbers are proposed, and the fork's model-A feasibility hinges on them. Spine evidence: proven-live PER-DOCUMENT text the panel reads is 8,000 bytes (CredenceLend FETCH_BYTES_CAP, 'every examined byte fits the prompt', 103 live tx) to 12,000 (InsureShield); proven item counts 6–12 (MAX_EVIDENCE 6, MAX_ACTIVE 8 + MAX_APPEAL 4); proven quote bounds 8/240/3; NOTE_CAP 200. Critically: NO spine ever carried more than ~1–2KB of user text in WRITE-TX calldata (TEXT_CAP 300, CLAIM_TEXT_CAP 800, REASON_CAP 500) — the only proven large-blob transit is the leader's nondet payload, which _parse_payload accepts up to 300,000 chars and which 103 live consensus rounds moved. So a ~100KB submit_assessment calldata write is UNPROVEN on StudioNet in either spine; model A's ceiling is an open empirical question, not a known-safe fact.
- fix: Adopt and publish in get_config: MAX_CLAIMS 12, MAX_EVIDENCE_ITEMS 10 (8 at submission + room for appeal), MAX_NEW_ITEMS_PER_APPEAL 4 (CredenceLend), PER_ITEM_TEXT_CAP 8000 chars (the 103-tx-proven figure; do not start at 12000), PACKET_BYTES_CAP 96000 (10×8000 + typed fields + margin — comparable to what the panel prompt already carried live), MAX_RUNS_PER_ASSESSMENT 4 (1 + 3 appeals; InsureShield MAX_ROUNDS 3 shape), QUOTE_MIN 8 / QUOTE_CAP 240 / MAX_QUOTES 3, NOTE_CAP 200, VIN fixed 17. De-risk the unproven single-tx ceiling structurally: stage the packet — begin_packet(manifest) → append_packet_part(id, seq, bytes) each verified against the pre-committed text_sha256 → seal_packet(root) makes it immutable — so no single write ever needs the untested ceiling, and probe actual limits on a disposable deploy before the canonical one (the model-diversity practice).

**[medium] ARCHITECTURE.md §4 contract surface — adjudicate/readjudicate preconditions and get_verdict semantics unstated**
- standard: S30 (two runs racing one assessment — the release-gate table itself names this test), S25, S26
- problem: The surface does not say who may call adjudicate/readjudicate, whether a second adjudicate can race a pending one, or which run get_verdict returns when several exist. The design's own release gate demands an invariant test for 'two runs racing one assessment' but the surface defines no guard for that test to verify; and an appeal filed while a run is mid-flight can interleave run numbering and manifest references.
- fix: Spec deltas: adjudicate/readjudicate refuse unless assessment state permits (exactly one run in flight; readjudicate only from ADJUDICATED; runs capped at MAX_RUNS_PER_ASSESSMENT with the contract's refusal sentence naming the cap — S40 surfaces it). Callable by the recorded seller or a recorded disputing buyer only (recorded parties, not any address). get_verdict returns the latest run whose status is terminal-success, plus the run number and total runs so no caller confuses a superseded verdict with the standing one; get_run(id, n) stays the historical read.

**[medium] ARCHITECTURE.md §4/§5 (evidence text in calldata; 'share links are signed, expiring, revocable') vs brief §15 'private-by-default evidence'**
- standard: S12 (the Aegis 'sealed' lesson: consensus requires every validator to read inputs; a public chain cannot hide judged content)
- problem: Under model A every adjudicated item's normalized text becomes permanent public calldata — revocable share links then govern only the app's copy while the chain copy is world-readable forever; under model B the hash-capability URL makes it effectively public at adjudication time. Either way 'private-by-default' cannot survive adjudication, and the current docs imply it does.
- fix: State the limitation exactly as Aegis was made to: evidence is private UNTIL an assessment is requested; requesting adjudication publishes the normalized text of cited items to the public record, and the UI says so at the request step. Redaction (brief §15) must therefore run BEFORE packet build, and the redacted text is what the manifest text_sha256 commits. Do not use 'private', 'sealed', or 'revocable' for anything that has entered a packet.


## Lens: product-scope

### Recommendation

Gap list, product-half lens: the architecture is faithful to the brief's spine (13 data models verbatim, full verdict enum, OCR-as-null honesty genuinely satisfies 'evidence never silently discarded', non-goals §3 all respected, no toy demo, no score gauges — I found no outright brief violations in what IS designed) but it silently drops one blocking and four high items: (1) BLOCKING — brief §15 private-by-default evidence is structurally violated by the current model-A text: normalized evidence text in calldata is permanently public on the explorer and unredactable, share-link revocation notwithstanding; from this lens the fork resolves to 'either model, plus mandatory pre-submission redaction, an explicit publicity-consent step at assessment time, and the boundary named in the threat model' — model A without those cannot claim §15/§16, and model B at least bounds exposure to link-holders and keeps text off permanent public state; (2) disputed-claim flags (three separate brief mentions) absent end-to-end; (3) the packet omits diagnostic observations, inspection findings, assessment rules, and prior-verdict-on-appeal, and diagnostic-code normalization — half the product's name — appears nowhere; (4) findings drop confidence, unresolved questions, and recommended next action, all mandatory verdict fields; (5) the corroboration floor the standards map advertises is sybil-defeatable via the seller's own share link, because COUNTERPARTY derives from a role anyone with the link can acquire. Mediums: unnamed serverless job driver (S26 mover missing), rate limiting/pagination/structured errors/observability all absent, no E2E-with-seeded-fixtures plan, no report export, screen 13 has no backing features, SOURCE_UNAVAILABLE is a dead enum value (S12 hazard). Every fix above is a docs/design addition, not a rebuild — but defects 1, 3, 4 and 5 change the packet schema and finding schema, so they must land before the contract is written, not after.

### Defects

**[blocking] ARCHITECTURE.md §4 (calldata evidence model) + §5 (ShareLink) — vs brief §15/§16/§6**
- standard: Brief §15 'private-by-default evidence', §16 'unauthorized users cannot access private evidence', §6 'redaction status' per item
- problem: Under model A, bounded normalized evidence text rides in calldata on StudioNet: it is readable by anyone via the public explorer/RPC, permanently, regardless of share-link revocation. ShareLink revocation revokes only the app's copy; redaction after submission is impossible because calldata is immutable. The docs never mention this tension, so §16's 'unauthorized users cannot access private evidence' proof is unfalsifiable as designed, and §6's per-item redaction status has no home.
- fix: Whichever side of the open fork wins: (1) redaction runs BEFORE packet build (per-item redaction status in EvidenceItem, redacted text is what enters the packet/served bytes); (2) an explicit consent step at 'generate assessment' states that adjudicated normalized text becomes effectively public (calldata) or public-to-link-holders (hash-capability URL); (3) unadjudicated evidence stays app-private; (4) the threat-model doc names this as the privacy boundary. Model A as currently written cannot claim brief §15 compliance without these.

**[high] ARCHITECTURE.md §3 packet composition + §7 state machines — design gap**
- standard: Brief §2 buyer 'flag a claim as disputed', §8 buyer step 5, §13 packet must contain 'disputed claims'
- problem: Disputed-claim flags appear nowhere: not in the packet field list (§3), not in the data model narrative, not in any state machine. The panel is never told which claims the buyer contests, though the brief requires it in the contract's input packet.
- fix: Add a per-claim dispute flag (buyer-role act on VehicleClaim, audit-evented), carried as a typed packet section and disclosed to the panel as the buyer's assertion (S31-symmetric: a dispute is a claim, not a fact). Dispute after a verdict enables a new run, same S33 shape as new evidence.

**[high] ARCHITECTURE.md §3 — the packet omits four brief-required sections; diagnostic-code normalization absent everywhere**
- standard: Brief §13 packet contents (diagnostic observations, inspection findings, source reliability labels, assessment rules, previous verdict on appeal); §11 'diagnostic-code normalization'; §2B is half the product
- problem: DiagnosticObservation and InspectionFinding exist only as Prisma rows (§5); the packet §3 builds carries vehicle facts, claims, evidence entries, pre-findings, manifest — no structured diagnostics section, no inspection-findings section, no assessment rules, and readjudicate's delta packet never says it includes the prior verdict (§13: 'previous verdict if this is an appeal'). 'Diagnostic-code normalization' (brief §11) is mentioned nowhere, though OBD-II code entry is a required screen (#7) and capability (§2B).
- fix: Add packet sections: normalized diagnostic observations (deterministic OBD-II parse — PXXXX format check, dedupe, code-formatted strings per the no-unit-arithmetic rule), structured inspection findings, and on appeal the appealed run's verdict reference. Map 'source reliability labels' explicitly to the corroboration-class + declared-type fields (record the substitution as a decision if that is the intent). Add diagnostic-code normalization to packages/validation with unit tests (brief §16 'diagnostic-code parsing').

**[high] ARCHITECTURE.md §4 (findings/equivalence) + §6 (verdict model) — design gap**
- standard: Brief §5 'every verdict must include: confidence level; unresolved questions; recommended next action'; §13 'confidence and severity'; §14 'explain what additional evidence would reduce uncertainty'
- problem: The finding schema is status, severity, evidence-id citations, quotes. Confidence is absent from both the findings and the equivalence field list; unresolved questions and recommended next action are absent everywhere (STANDARDS-MAP §3 covers the what-would-lift-it sentence only for the corroboration-floor case, not for uncertain findings generally).
- fix: Add per-claim confidence as a bounded band enum inside equivalence (it is downstream-read, so S7 puts it in the agreed set), plus unresolved_questions and recommended_next_action as bounded text fields validated at the boundary. Render confidence as a labeled band with named grounds, never a numeric gauge — the brief's §10 'no meaningless AI score gauges' constrains the display, not the field.

**[high] ARCHITECTURE.md §2 (roles: 'a buyer on assessments shared with them') + §3 (CORROBORATED class) — design gap**
- standard: Brief §6 'whether it is independently corroborated', §7 'source impersonation'; S27/S34 (subject controls identity → floor in code)
- problem: COUNTERPARTY/CORROBORATED derive from account role, and buyer role derives from opening a share link. A seller can open their own share link with a second free account, upload 'buyer' evidence, and the deterministic code derives CORROBORATED ('two or more items from parties with opposing interests'), lifting FIRST_PARTY-only claims past the exact floor the standards map advertises as pricing seller self-dealing. The floor is defeated by a sybil the design itself enables.
- fix: State that role-derived COUNTERPARTY is asserted independence, not proven: either reserve CORROBORATED for the integrity-bound independent-source path already named (registrable-source binding) and treat opposing-role uploads as a distinct class that lifts only to PARTIALLY_VERIFIED, or keep the current derivation but document the sybil limit in the evidence trust model and disclose uploader account age/linkage class to the panel. The docs must stop implying the floor is sybil-proof.

**[medium] ARCHITECTURE.md §2 (background work) — serverless job driver unnamed**
- standard: Brief §11 'assessment job queue'; S26 every non-terminal state names its mover
- problem: 'In serverless deployment an authenticated route triggers the same function' — but nothing is named that calls the route. In the serverless deployment PROCESSING has no mover, so the S26 timeout exit the standards map promises has no actor either; jobs stall silently.
- fix: Name the driver: a platform cron (e.g. Vercel cron) hitting the authenticated drain route on a fixed cadence, with a job lease + bounded retry so a dead invocation cannot strand PROCESSING; or record explicitly that serverless deploys require an external scheduler and the supported deployment runs apps/worker. One sentence in §2 plus the lease design.

**[medium] ARCHITECTURE.md §2/§9 — backend requirement list silently dropped**
- standard: Brief §11 rate limiting, pagination, structured error responses, observability hooks; §15 rate limits
- problem: None of the four appear anywhere in either doc (grep-confirmed). Rate limiting is doubly required (§11 and §15) and guards the expensive adjudication path; pagination and a typed error envelope are named backend requirements; observability hooks likewise.
- fix: Add to the stack section: deterministic token-bucket rate limiting (per session and per IP) on upload and assessment-trigger routes; cursor pagination on all list endpoints; one typed error envelope ({code, message, details}) used by every route — which also carries the contract's verbatim refusal sentence the S40 section promises; a minimal structured request-log hook. All app-side, no contract impact.

**[medium] ARCHITECTURE.md §9 delivery order — E2E tier and seed fixtures absent**
- standard: Brief §16 'Test the complete seller-to-buyer journey using seeded fixtures'; §9 tree tests/e2e; §19 acceptance
- problem: Delivery names the direct-mode suite and integration tests only. No E2E plan, no seeded fixtures anywhere in the docs, so the one journey the brief singles out (seller create → evidence → assess → share → buyer counter-evidence → dispute → reassess → verdict → revoke link) has no planned proof.
- fix: Add a committed deterministic seed script (fixture vehicles + evidence files with known sha256s, so manifest hashes are assertable) and a browser E2E (Playwright) of the full journey including share-link revocation returning 404/410. Slot it into phase 4-5 of §9.

**[medium] ARCHITECTURE.md — brief §8 buyer step 8 dropped**
- standard: Brief §8 'Export or share an assessment report'
- problem: Export appears nowhere in the docs. Sharing is covered by ShareLink; export is not.
- fix: Minimal honest design: a print-styled report view (or server-rendered PDF) of the verdict screen carrying the manifest root, contract address+version, and adjudication tx reference — a portable restatement of the on-chain record, adding no new trust surface.

**[medium] ARCHITECTURE.md — brief §10 screen 13 has no backing features**
- standard: Brief §10 required screen 'account and privacy settings'; §15 redaction support
- problem: No privacy controls exist anywhere in the design for that screen to expose: nothing says what a user can see, revoke, redact, or delete about their evidence — and under the calldata model, adjudicated text cannot be deleted at all, which the screen would have to say truthfully.
- fix: Define the settings surface: profile + session management, the user's evidence list with visibility state, pre-submission redaction controls (defect 1), and an honest statement of what becomes permanent once adjudicated. Design it with defect 1's resolution, not after it.

**[medium] ARCHITECTURE.md §6 — SOURCE_UNAVAILABLE is a dead enum value**
- standard: Brief §13 'if external information is unavailable, return SOURCE_UNAVAILABLE'; S12 narrative honesty (release gate in STANDARDS-MAP)
- problem: The full brief enum is adopted, but §4 forbids all contract-side fetches, so no path can ever produce SOURCE_UNAVAILABLE. A verdict value the README will document but the code can never emit is a standing S12 violation in waiting.
- fix: Either define its producing condition app-side (an evidence item of class 'external source result' declared but unreachable/unextracted at packet time yields SOURCE_UNAVAILABLE for claims resting on it) or mark it reserved-and-unreachable in the verdict-model doc with the reason (no contract-side fetch by S39 design).

**[low] ARCHITECTURE.md §2/§3 — evidence taxonomy and per-item fields thinner than brief §6**
- standard: Brief §6: 12 evidence classes incl. video, government/import documents, manual observation, external source result; per-item MIME type and chain-of-custody events
- problem: The docs handle PDF/image/text. Video is never mentioned; the class taxonomy is not enumerated; MIME type and per-item chain-of-custody events are absent from the packet field list (AuditEvent exists but is not bound per evidence item).
- fix: Enumerate the full class enum in packages/shared-types; video is stored, hashed, extraction_status UNAVAILABLE (the same honesty already designed for OCR-less images); include MIME type in EvidenceItem and the packet metadata; per-item custody = AuditEvent rows keyed by evidence id, surfaced on the evidence review screen.

**[low] ARCHITECTURE.md §4 — caller-role matrix for contract-triggering acts unspecified**
- standard: Brief §2 buyer 'request an assessment'; §8 buyer step 6 'request reassessment'; S40 act availability as pure function
- problem: The S40 section promises act availability as a pure function of (record, role, state) but neither doc states which roles may trigger adjudicate/readjudicate. The brief grants buyers the right to request assessment and reassessment; the seller-centric flow in §3 leaves this ambiguous.
- fix: Write the role × act matrix into the architecture (seller: submit+adjudicate; buyer: request reassessment after adding evidence or flagging disputes; either: retry FAILED) — it is the exact input the promised pure-function test file needs.

**[low] ARCHITECTURE.md §2 — upload security thinner than brief §15**
- standard: Brief §15 malware/file-type validation, malicious filenames and metadata, safe rendering of extracted document text
- problem: Only 'size/type validation' is mentioned. Content sniffing vs extension trust, filename handling, and how extracted evidence text is rendered (it is attacker-authored — an XSS vector if ever rendered as HTML) are unaddressed.
- fix: Magic-byte type sniffing (never trust extension/declared MIME), stored name divorced from upload filename (hash-derived), extracted text rendered exclusively as plain text, and 'no antivirus scanning' recorded as a stated limitation in the threat model rather than implied coverage.
